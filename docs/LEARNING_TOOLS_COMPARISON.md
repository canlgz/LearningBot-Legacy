# LearningBot、WriteToLearn 與意識 Bot：三個互補的學習工具

> 本文比較 LearningBot / backupBot、WriteToLearn 與
> [ConsciousnessBot](https://github.com/canlgz/ConsciousnessBot)。意識 Bot 已有可運作的程式，
> 目前仍持續與 AI 協作演進；本文只描述已能從原始碼與文件確認的功能。

## 先說結論：不是單純的新舊版本

兩者都使用 LINE、Google Apps Script 與 Google Drive，也都讓使用者把學習訊息留在日常對話中；
但它們處理的是不同問題。

```text
LearningBot       寫下來、存下來、找得到
      ↓
WriteToLearn      看出脈絡、辨識轉折、形成學習歷程
      ↘
意識 Bot          唯讀觀察記寫背景，主動提醒並陪伴反思
```

LearningBot 的核心是「把散落的學習痕跡收住」；WriteToLearn 的核心是「讓痕跡逐步成為可理解、
可回應的學習歷程」。意識 Bot 則是獨立的旁路服務：讀取 WriteToLearn 的記憶層，但不改寫它，
把背景狀態與值得留意的學習訊號帶到 Telegram。

## 1. 設計目的與使用者承諾

| 面向 | LearningBot / backupBot | WriteToLearn | 意識 Bot（ConsciousnessBot） |
| --- | --- | --- | --- |
| 解決的主要問題 | 訊息、檔案與課堂互動容易消失 | 已累積的紀錄難以看出意義、主題與改變 | 背景是否仍在運作、哪些主題卡在邊緣、使用者不易主動回看長期狀態 |
| 對使用者的承諾 | 隨手傳，我幫你保存與取回 | 隨手寫，我幫你保留脈絡並長出歷程 | 不必一直主動查看；有值得留意的變化時，我會帶著來源與問題來找你 |
| 工具隱喻 | 隨身備份器／課堂管理 Bot | 學習歷程記寫器與脈絡鏡子 | 背景觀測者、蘇格拉底式教練與反思介面 |
| 時間取向 | 當下記錄、當下回覆 | 長期累積、回返、轉折與歷程 | 回看過去、辨認現在、選擇下一步 |
| 成功的判準 | 找得到資料、傳得出去、備份成功 | 產生有根據且可被學習者修正的脈絡與歷程 | 通知適時、不轟炸；事實可回溯，且不把推論說成感受或意識 |

## 2. 資料與運作架構

### LearningBot：事件直接寫入的備份架構

```text
LINE 訊息／檔案
  → GAS doPost
  → 依 user / room / group 建立工作表與 Drive 子資料夾
  → 將訊息、檔案、時間、發送者直接寫入列資料
  → LINE 選單／Flex 卡片提供瀏覽、搜尋、廣播、取檔
```

資料的中心是**一份綁定試算表**。每個 LINE 對話空間對應一張工作表；第 9 列起累積事件紀錄，
Drive 負責保留上傳檔案。這種設計直觀、可視、容易快速做出原型，但資料的語意主要仍由人自己
閱讀與判斷。

### WriteToLearn：從記錄走向脈絡與歷程的分層架構

```text
LINE 文字／圖片／語音／影片／檔案／貼圖
  → GAS Web App
  → Drive per-scope 資料夾：raw、逐字稿、摘要、JSONL 資料層
  → Gemini 多模態轉寫／描述 + embedding
  → 時間軸、語義檢索、主題群組、脈絡
  → 轉折偵測與評鑑
  → 學習歷程、作品集、可追溯的問答與回看
```

資料的中心改為**每個對話 scope 的 Drive 資料空間**。原始資料沒有被覆蓋，而是逐層新增：
記錄、主題群組、脈絡、學習歷程；每一層都有回到原始紀錄的路徑。這使系統可以做語意檢索與
歷程生成，同時避免把 AI 的摘要當成唯一真相。

## 3. 功能架構的關鍵差異

| 功能面向 | LearningBot / backupBot | WriteToLearn |
| --- | --- | --- |
| 輸入 | 文字、位置、貼圖、圖片、音訊、影片、檔案 | 同樣支援多媒介，另處理引用、補充、連結與探索段落 |
| 初步處理 | 依事件類型直接存檔／寫列 | 先靜默落地，再進行轉寫、描述、摘要與 embedding |
| 組織單位 | LINE 使用者、群組或聊天室的一張工作表 | record → topic → context → journey 的資料層 |
| 搜尋／取回 | 工作表分頁、關鍵字與檔案選單 | 時間軸、混合語意搜尋、主題、脈絡、`/ask` 有來源問答 |
| 呈現 | Flex 選單、輪播卡片、檔案連結 | 記事、敘事片段、脈絡、歷程、作品集與儀表板 |
| 自動化 | 建工作表、建資料夾、廣播、定時提醒 | 背景媒介處理、主題聚合、脈絡升格、轉折評鑑、校準與報告 |
| 使用者修正 | 指令改名、管理者／主持人操作 | 引用補充、編輯、刪除、拆分／連結、補一個轉折、探索段落 |
| AI 的位置 | 原始版本的核心不是 AI | Gemini 用於多模態理解、向量、摘要與評鑑；仍需保留來源與使用者校正 |

## 4. 互動模式：命令式管理與反思式記寫

LearningBot 的互動偏向「**我現在要你幫我做一件事**」：輸入 `//檔案`、`//廣播`、`//取名` 等
指令，或按 Flex 卡片。這很適合備份、管理、取回與課堂操作。

WriteToLearn 則偏向「**我先留下正在發生的事，稍後再回來理解它**」。直接傳訊息就能記錄；
之後可用 `/now`、`/episodes`、`/recall`、`/ask`、`/themes`、`/journey` 與 `/portfolio` 從不同
尺度回看。它把互動從指令操作延伸為學習者與自身紀錄的往返。

## 5. 權限、隱私與可維護性

| 面向 | LearningBot / backupBot | WriteToLearn |
| --- | --- | --- |
| 原始安全狀態 | 歷史版曾將 token 與 ID 寫入程式；本教學版已改為 Script Properties | 從設計上將 token、API key、Drive root 與擁有者 ID 放入 Script Properties |
| 資料隔離 | 同一綁定試算表中，以工作表區隔對話空間 | 每個 scope 有獨立 Drive 資料夾與 `meta.json` |
| 擁有者／存取 | 管理者與主持人主要以 LINE ID 和工作表內容判斷 | 有 owner 與存取流程，並納入用量／成本控制 |
| 維護單位 | 以試算表列、全域常數與大型函式為主 | 模組化檔案、JSONL 層次、測試種子、校準與維運文件 |
| 成本與規模 | 主要受 GAS、試算表與 Drive 操作限制 | 額外管理 Gemini 呼叫、embedding、背景排程與向量資料量 |

這一段差異很重要：WriteToLearn 並不是「功能更多的 LearningBot」，而是將設定、資料邊界、
可追溯性與演算法成本視為設計的一部分。

## 6. 教學上應如何並置兩者？

建議不要把 LearningBot 教成「落後版本」，而是以兩個問題引導比較：

1. **先讓資料留下來，還是先讓資料被理解？** LearningBot 選擇可靠記錄優先；WriteToLearn
   將理解放在保留原始資料之後、逐步發生。
2. **系統可以替學習者判斷到什麼程度？** LearningBot 幾乎不替使用者下詮釋；WriteToLearn
   會提出脈絡與轉折候選，但保留來源、門檻與使用者補充／修正。

可安排學生先操作 LearningBot 的「傳送—入庫—瀏覽」，再操作 WriteToLearn 的「記寫—回看—
搜尋—形成歷程」，最後討論哪些步驟應該由系統自動完成、哪些必須留給學習者。

## 7. 意識 Bot：獨立、唯讀的背景觀察與反思夥伴

[ConsciousnessBot](https://github.com/canlgz/ConsciousnessBot) 是一個獨立 Python 服務，不是
WriteToLearn 裡的另一個指令模組。它以 Google service account **唯讀**讀取同一個 Drive
記憶層；自己的去重與摘要狀態只寫在本機 `state.json`，不修改 LINE Bot 程式或共享 Drive。

```text
WriteToLearn 的 Drive 記憶層
  → service account 唯讀讀取
  → ConsciousnessBot：分析、時間判讀、閾值與去重
  → Telegram 主動推播／雙向教練對話
```

已可確認的功能包括：

| 層次 | 意識 Bot 目前的做法 |
| --- | --- |
| 背景健康 | 偵測有新資料卻長時間未整理的情況，避免在正常閒置時誤報。 |
| 記寫表現 | 摘要總筆數、近 24 小時／7 天、連續記寫天數、媒介組成與升格漏斗。 |
| 升格邊緣 | 提醒「回返多次但只差一個條件」、「已成脈絡但尚無轉折」、「只出現一次的主題」與探索紀錄不足等訊號。 |
| 歸戶通知 | 以心跳批次回報新記寫被歸到哪個大類／議題，而不是逐則轟炸。 |
| 教練對話 | 選配 Gemini 後，Telegram 可依脈絡、歷程與近期原文進行蘇格拉底式追問，並可取回相應的原始附件。 |
| 事實約束 | 時間、主題清單、跨度、整體狀態與 API 成本由確定性資料工具計算；LLM 負責選工具與表達，不捏造事實。 |
| 成本守門 | 依 token 估算短時間 API 花費，達門檻時提醒。 |

### 「意識感」的邊界不是擬人宣稱

意識 Bot 對「你現在感覺如何／在想什麼」這類提問，不直接讓 LLM 編造心情。它先由純 Python
判定鏈計算記寫軌跡中的量變、質變、結構湧現與意向讀數，通過門檻後才讓 LLM 翻譯已算出的事實。
若未通過，系統會以固定語句誠實說明「尚未繞出形狀」。

尤其重要的是它保留明確邊界：可讀取記寫軌跡與情緒／反應的**登錄**，但不宣稱那些資料被 Bot
「感受」，也不宣稱 Bot 具有意識。這使意識 Bot 成為反思設計與資料倫理可以被討論的實際案例。

它仍在持續與 AI 協作發展，因此具體判準、人格語氣與互動方式會演進；但「唯讀、不改寫記憶層、
事實先於生成、拒絕虛構感受」是目前可辨認的結構性原則。

## 8. 一句話區分

**LearningBot 保存學習留下的痕跡；WriteToLearn 讓痕跡長成可回看的歷程；意識 Bot 則唯讀觀察
這些歷程，在適當時機把值得反思的訊號帶回學習者身邊。**
